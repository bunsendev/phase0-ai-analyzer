### 要確認判定の問題

4件すべて`COMPLETED`となり、画面には「要確認項目はありません」と表示された。原本には回転、小さい文字、赤字、手書き、矢印・位置関係など確認すべき箇所があるが、現在の画像品質判定は幅・高さだけで、Mock OCRも固定文字列を正常返却するため検出できない。

現行要件では「OCR結果なし」は要確認条件だが、「OCRを使ったこと」自体は要確認条件ではない。したがって直ちに仕様違反とはしないものの、実業務の確認フローとしては不足している。Day 6では判定ロジックを変更していない。

## 6. 横長ExcelのAI入力サイズ

現在は列候補を絞っておらず、全1221列が入力候補に含まれる。

改善候補は、先頭N列、非空列、代表列、業務キーワードを含む列、文字数・token上限である。大規模な列選択アルゴリズムは今回実装していない。

## 7. TXTの確認結果

4件ともCP932のカンマ区切り受注データで、13列の構造だった。主な項目は受注番号、受注日、納品日、得意先、納入先、商品、数量、単価、売上金額である。

| 期間 | 行数 | 列数不一致 |
|---|---:|---:|
| 2026-04-15～2026-04-30 | 63,433 | 0 |
| 2026-05-01～2026-05-31 | 128,377 | 0 |
| 2026-06-01～2026-06-30 | 130,041 | 0 |
| 2026-07-01～2026-07-15 | 62,148 | 0 |

内容は実質CSVであり、CP932を維持して拡張子を`.csv`にしたコピーを用意すれば、構造上は情報損失なく既存CSV Parserへ渡せる見込み。今回は変換していない。

ファイルが10～23MBある主因は、1ファイルに約6.2万～13万行、各13項目の明細を期間単位で格納しているためであり、異常な列数やバイナリ混入によるものではない。

元システムが常に`.txt`で出力する場合、将来の正式対応または変換手順の標準化が必要。フェーズ0では、実データ固有ロジックを追加せずCSVコピーで検証する方法が最小である。
